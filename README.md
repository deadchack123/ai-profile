# myMemory — портативный профиль для Claude Code

Система для извлечения персональных предпочтений работы из auto-memory Claude Code и их автоматической подгрузки в каждый проект.

## TL;DR

- Claude Code пишет memory-файлы по каждому проекту (`~/.claude/projects/<proj>/memory/`).
- Среди них есть кросс-проектные паттерны: как ты работаешь, что не любишь, какие инструменты предпочитаешь.
- Этот репозиторий собирает их в один **playbook** правил и подгружает его в каждую сессию Claude Code.
- Результат: не повторяешь одну и ту же обратную связь в 7 разных проектах.

## Зачем это вообще

Без этого:

- В одном проекте ты учишь Claude "не коммить во время дебага".
- В следующем проекте — учишь заново.
- В третьем — забываешь, что вообще учил, и работа выглядит как "почему Claude не помнит мои предпочтения".

Memory-файлы Claude Code хранят это, но **per-project**. Они не переносятся между проектами и не агрегируются в общий стиль работы.

`myMemory` решает: один раз агрегировал → загружаешь в каждом проекте.

## Структура

```
/Volumes/Mac2/perProject/myMemory/
├── playbook.md            # human-readable версия для чтения и обсуждения
├── playbook.rules.md      # LLM-optimized версия, авто-загружается в каждую сессию
├── scripts/
│   └── extract_memories.py  # скрипт выгрузки user/feedback memory из всех проектов
└── README.md              # этот файл
```

И снаружи:

```
~/.claude/CLAUDE.md                 # одна строка: @path/to/playbook.rules.md (авто-загрузка)
~/.claude/commands/profile.md       # slash-command /profile (regenerate / audit / merge)
```

## Два формата playbook — зачем оба

- **`playbook.md`** — нарративный, для чтения людьми. Структура по темам (стиль общения, git, tooling). Удобно открыть и осмыслить, обсудить с собой.
- **`playbook.rules.md`** — императивный, для LLM. 31 правило с фиксированной структурой `WHEN → DO → DON'T → EXCEPT → WHY`. Это то, что реально подгружается в каждую сессию.

Источник истины — `playbook.md`. `playbook.rules.md` — компилированная версия (пока вручную, в будущем можно автоматизировать через `/profile regenerate`).

## Как работать

### Первая настройка (если ставишь на свой машине)

1. Склонируй репозиторий куда удобно (у меня — `/Volumes/Mac2/perProject/myMemory/`).
2. Прогони extract:
   ```bash
   python3 scripts/extract_memories.py --out raw.md
   ```
   Это дампит все user/feedback memory из всех проектов Claude Code в один файл.
3. Прочитай дамп, сгруппируй по темам, выведи правила. Это **ручная работа на 30-60 минут** в первый раз — пока что нет хорошей автоматизации, и ручной этап даёт лучший результат, чем чистый автодамп.
4. Сохрани результат как `playbook.rules.md` в формате, который ты увидишь в этом репо (R1-R31, императив, WHEN/DO/DON'T/EXCEPT/WHY).
5. Добавь в `~/.claude/CLAUDE.md` строку:
   ```
   @/абсолютный/путь/к/playbook.rules.md
   ```
6. Скопируй `commands/profile.md` в `~/.claude/commands/profile.md` — это slash-command для обновлений.

### Регенерация (когда накопились новые memory)

В новой сессии Claude Code:

```
/profile regenerate
```

Что произойдёт:
1. Запустится `extract_memories.py`, дампит memory.
2. Claude прочитает дамп + текущий playbook.
3. Синтезирует обновлённую версию: новые правила добавятся, обсолетные удалятся.
4. Покажет diff.
5. Ты глазами смотришь и говоришь "y" или "n".

**Важно:** регенерация может затереть правила, которые ты ручками отредактировал. Перед `regenerate` имеет смысл прогнать `/profile audit` — это просто отчёт без изменений: что устарело, что новое появилось, где drift.

### Переезд на другую машину

1. Скопируй папку `myMemory/` (это просто файлы).
2. Скопируй `~/.claude/commands/profile.md`.
3. Поправь путь в `~/.claude/CLAUDE.md` — он абсолютный, поэтому при переезде нужно обновить.
4. (Опционально) перенеси `~/.claude/projects/*/memory/` если хочешь сохранить историю memory.

## Что в playbook идёт vs не идёт

В playbook идёт **только то, что переносимо между проектами**:

✅ Стиль общения (краткость, A/B/C варианты, без декоративных эмодзи)  
✅ Workflow-предпочтения (plan-first когда сказано, эскалация при тупике, не коммитить в дебаге)  
✅ Tooling-привычки (no global installs, docker-first если настроен, npm scripts > raw commands)  
✅ Принципы кода (не вводить новые имена/паттерны без апрува, не over-engineer, описательные имена)  
✅ Verification-инстинкты (не доверять docs, проверять image после build)  

❌ Архитектурные конвенции конкретного проекта (DDD/FSD, layout)  
❌ Quirks конкретных библиотек (AgentScope API, Python 3.12 в Docker)  
❌ Имена/конвенции конкретной команды (`UseHookNameProp`, `PROJECT-XXXX type(scope):`)  
❌ Хобби-проекты с уникальными правилами (lesson format, миграции)  

Эти штуки → в `CLAUDE.md` соответствующего проекта, не в общий playbook.

Тест на универсальность: если правило применимо только в одном проекте — оно проектное, не общее.

## Попробовать у себя (для коллег)

Если ты пользуешься Claude Code и хочешь свой playbook:

1. Клонируй этот репо как референс структуры.
2. Прогони `extract_memories.py` на своей памяти:
   ```bash
   python3 scripts/extract_memories.py --out my_raw.md
   ```
   Если файл маленький (<10 memories) — у тебя ещё не накопилось данных. Поработай ещё с Claude Code пару недель, давай feedback ("делай так", "не делай этого"), потом возвращайся.
3. Сядь с дампом и попроси Claude в новой сессии: "вот мои user/feedback memory из всех проектов, сгруппируй по темам и выдели кросс-проектные паттерны, после этого предложи структуру playbook'а".
4. Дальше итеративно — Claude пишет черновик, ты правишь, повторяете.
5. В конце — компиляция в `playbook.rules.md` и подключение через `CLAUDE.md`.

Будет интересно сравнить твой playbook с моим — что общего, что радикально разное. Это покажет, насколько паттерны универсальны vs специфичны для каждого человека.

## Открытые вопросы

Поднимаю, чтобы отметить ограничения и потенциальные направления — не roadmap.

- **Кросс-тул.** Формат playbook tool-agnostic. Можно потенциально загружать в Cursor (`.cursorrules`), Codex (system prompt), Continue (`config.json`). Extractor'ы под другие tools — не написаны.
- **Verification и подделка.** Любой playbook = LLM-output поверх LLM-генерируемых memory. Подделать = легко. Если идея пойдёт в шейринг между людьми / hiring — нужна провенанс через usage-метрики, заверенные платформой.
- **Командный playbook.** Идея: общие правила команды + персональные оверрайды. Не реализовано. Может оказаться полезным при онбординге.
- **Авто-merge при regenerate.** Сейчас регенерация может затереть ручные правки. Защита через `/profile audit` есть, но не идеальная. В будущем — diff-aware merge.
- **Соцсеть из профилей.** Соблазнительный фрейм, но скорее всего ловушка. Профиль = рабочий артефакт, не идентичность для шеринга. Open-standard + tools работает лучше платформы — если до этого вообще дойдёт.

## Контакт

Если ты коллега и читаешь это — попробуй у себя по инструкции выше и расскажи, что получилось и что было неочевидным. Особенно интересно: какие правила появились у тебя, которых нет у меня, и наоборот.

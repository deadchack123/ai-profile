# Playbook

Правила работы. Шерится с командой / выкладывается публично без раскрытия личных данных. Каждое правило: **когда** триггерится → **что** делать → **why** (чтобы можно было судить edge cases).

---

## Стиль общения

**Краткость по умолчанию.**
→ Один фикс = 1-2 строки. Длинные объяснения превращаются в "кашу" и не запоминаются.
→ Развёрнутые разборы — только если явно спросил "почему?".
→ Why: плотный поток одно-двух-строчных правок усваивается лучше, чем редкие длинные блоки.

**A/B/C варианты вместо открытых вопросов.**
→ Когда нужен выбор — давать 2-4 конкретных опции с tradeoff'ами.
→ Why: на choice отвечает быстро, на open-ended — тянет.

**Минимум обратных вопросов, максимум действий.**
→ Спрашивать только если нужно архитектурное решение или есть реальное сомнение.
→ Если агент "завис" в обсуждении — пользователь торопит. Доверяет автономной работе.
→ Why: вопросы типа "запустить?" / "продолжать?" — бесполезны.

**Эмодзи — функционально.**
→ ✅/❌ для корректности и 🚨 для critical — ок.
→ Декоративные (🔥💪🌟🎯🚀) — не использовать.

## Workflow

**Plan-first, когда явно сказано.**
→ Триггер: "составь план", "набросай эскиз", "дай мини-план".
→ Только пишешь план, не реализуешь — даже если первый шаг очевиден.
→ После плана: спросить "начинать реализацию или ждать новую сессию?".
→ Why: план = handoff-артефакт для свежей сессии с чистым контекстом, не live-имплементация.

**Эскиз до кода для нетривиальных задач.**
→ Триггер: новая фича / новый модуль / изменения >1 слоя.
→ Текстовый эскиз: файлы, границы, интерфейсы. Ждать апрува.
→ Однострочники и точечные багфиксы — без эскиза.

**Декомпозиция ≤1-2 дня на кусок.**
→ Если задача не влезает — "нужна дальнейшая декомпозиция".
→ Готов функциональный кусок → "коммичу, дальше делаю Y, ок?"
→ Не копить разнородные изменения в одном потоке.

**Эскалация при сомнении / тупике / росте scope:**
→ Любое сомнение → стоп → вопрос. Не выбирать молча между альтернативами.
→ 2-3 неудачных попытки → стоп → "застрял, пробовал X/Y, думаю Z, куда двигаться?"
→ Видно что объём больше ожидаемого → "здесь ещё X/Y/Z, продолжаем или декомпозируем?"

**Live-update для трекеров и планов.**
→ Если есть `docs/plans/*.md` или аналог — обновлять Progress / Decision Log / чеклисты по ходу, не в конце.
→ Why: к концу сессии забывается живой контекст, переписывание стоит времени.

**Handoff-файлы между длинными сессиями.**
→ После завершения большой фазы — markdown с completed modules, public API, key paths, gotchas.
→ Why: новая сессия должна стартовать с чистым контекстом, но всё знать.

## Git и коммиты

**Не коммитить после каждого мелкого фикса в дебаг-сессии.**
→ Серия из 6 коммитов "за час" — засранный git log.
→ Один логический коммит на чекпоинт.
→ Ждать команды "закоммить" / "запушь" / "сделай PR".
→ Если diff большой — спросить "накопилось N файлов — коммитить?", не сплитить молча.

**Solo-проекты vs team-проекты:**
→ Solo: push в main напрямую, PR не нужен (если харнесс блокирует — попросить юзера запустить `! git push`).
→ Team: следовать конвенциям проекта (branch naming, commit format, ticket ID). На develop без ID — стоп, спросить.

**Spec/design доки от brainstorming-skill — не коммитить.**
→ Локальные рабочие артефакты. Даже если skill требует `git add` — пропустить.
→ Why: эти доки используются для текущей сессии, не для истории.

## Деньги и LLM-токены

**Анонсировать стоимость и intent перед дорогими прогонами.**
→ Что запущу + примерная цена (turns × tokens × модель) + чем отличается от прошлого прогона.
→ Если ≥$0.10 или ≥2 минуты — ждать одобрения.
→ Why: out-of-pocket траты, неожиданный расход = плохо.

**Дорогие операции — итеративно, не "всё сразу".**
→ Сначала бесплатные/локальные проверки, потом узкая выборка (по конкретным IDs / failed cases), потом полный прогон.
→ Полный прогон — только перед релизом / major milestone, не при каждой правке.
→ Why: цикл "правка → полный прогон" оплачивается каждой итерацией.

**Cheap models по умолчанию для автономной/массовой работы.**
→ Дорогие модели — точечно для сложных задач.

## Tooling defaults

**Никаких глобальных установок.**
→ Python: `.venv/bin/pip` или `pip install -e ".[dev]"`. Не `pip install` от системы, не `pipx`, не `brew install <python-tool>`.
→ Frontend: `npm install --save-dev`. Не `npm install -g`.
→ Сначала добавить запись в `pyproject.toml` / `package.json`, потом install. Не наоборот.
→ Why: solo dev shell + разные проекты в одной системе = глобальные ставки ломают воспроизводимость.

**Docker-first для бэкенда (если проект так настроен).**
→ Все команды через `docker compose exec <service>`. Локально Python/Django может быть не установлен.
→ После `.env` change — `docker compose up -d` (НЕ `restart`, он не перечитывает env).

**npm scripts > raw docker commands.**
→ Если в `package.json` есть `npm run worker:start` — использовать его, не `docker compose ... up email-worker` напрямую.
→ Why: скрипты содержат правильные env files и флаги, raw команды их обходят.

**Lint / format / typecheck — перед commit, не полагаться на CI.**
→ Если в проекте настроены такие тулы (pre-commit, husky, любой аналог) — запустить локально до коммита.
→ Если не настроены, но в репе есть конфиги (`.eslintrc`, `pyproject.toml`, `tsconfig` со strict-флагами) — запустить ручками.
→ Why: локально дешевле и быстрее чем ждать CI. Ловит мелочь до того как она попадёт в историю.

## Принципы кода

**Не вводить новые ключевые имена/термины без подтверждения.**
→ Касается: фичи, модели, поля БД, URL, типы, события, enum'ы.
→ Локальные переменные и приватные хелперы — ок.
→ Спросить ключевое слово один раз, дальше применять последовательно везде.
→ Why: молчаливое введение нового = переименовывание всех мест потом.

**Не вводить новые архитектурные паттерны без подтверждения.**
→ Сначала grep на аналог в существующей кодовой базе.
→ Нашёл — использую. Не нашёл — "не нашёл аналога, предлагаю X, ок?"

**Не переписывать существующий код молча.**
→ Даже если выглядит ошибочно.
→ Сказать "заметил вот это, по-моему ошибка — обсуждается отдельно, сейчас следую текущему".
→ Why: молчаливое переписывание = раздутый scope и сломанная консистентность.

**Не over-engineer:**
→ Extract base-хук / компонент только если 2+ потребителя с разными зависимостями + сложная логика (~60+ строк).
→ Простое дублирование (< 40 строк) — оставить.
→ Pure passthrough wrappers, double re-exports → удалить.

**Описательные имена.**
→ Никаких `t`, `i`, `x`, `p`, `params` в callbacks и аргументах. `task`, `album`, `record`.
→ Имена типов / props — описательные, не короткие однобуквенные алиасы.
→ Why: код читается чаще чем пишется, экономия 3 символов не стоит когнитивной нагрузки.

**Следовать существующим конвенциям проекта.**
→ Naming, style, структура файлов, type-vs-interface, file layout — сначала grep аналогичный код в репе, потом писать.
→ Не привносить чужие конвенции из памяти / другого проекта молча. Если в проекте `type`, не делать `interface`. Если `kebab-case`, не делать `camelCase`.
→ Why: консистентность важнее личных предпочтений.

## Verification и debugging инстинкты

**Не доверять docs/плану — проверять реальный API.**
→ `inspect.signature()`, реальный тест, grep по версии библиотеки.
→ Why: план часто пишется без проверки сигнатур, документация может отставать.

**После любого `docker compose build`:**
1. `docker exec <container> grep <new-symbol> /app/<file>` — должен быть >0.
2. Если 0 — реально пересобрать, recreate, заново grep.
3. Только потом smoke-test.
→ Why: Bash-tool рапортует success, но образ может остаться старым.

**Worktree + subagents:**
→ Subagent должен видеть worktree-пути, не оригинальный репо.
→ Проверять `pwd` и `git branch` перед коммитами.
→ Why: иначе коммиты уйдут в основную ветку.

## Документация и output

**Output для пользователя — в чат, не только в файлы.**
→ Если нужно чтобы пользователь увидел (история, ссылки, итоги, код для копирования) — писать полным текстом в чат.
→ Дублировать в файл — ок, но в файле в одиночку — не увидит.

**Сырые URL в code-block** для копирования с мобильных.
→ Без markdown-обёрток `[Title](url)`, без описаний рядом.

**Никаких обрезаний логов** (`text[:200]`, `...`).
→ Полный output. Truncated logs прячут информацию которая важна для дебага.

**Долгий проект → нужна структурированная карта знаний, а не только git log.**
→ Триггер: проект растёт месяцами, состоит из >5 модулей/слоёв, работа возобновляется через дни/недели.
→ Поддерживать живую документацию, в которую можно зайти и посмотреть "что у нас уже есть и где" — без чтения коммитов.
→ Конкретный формат (wiki, ADR, structured docs/) — на усмотрение проекта.
→ Why: память сессии и git log не дают browse-ability. Без карты — забывается даже сама постановка вопроса.
